# Git & GitHub 프로젝트 투입 과정 Teaching Plan

## 과정 목표

학생은 Git 명령을 암기하는 데서 끝나지 않고 프로젝트 저장소의 현재 상태를 진단한다. 기능 브랜치에서 작은 커밋을 만들고, 원격 변경을 안전하게 반영하고, 충돌을 해결한 뒤 Pull Request로 협업한다.

## 운영 범위

### 판단·복구 확장

기본 4시간의 정상 협업 흐름은 유지한다. 내부 원리와 그림은 해당 개념 설명에 통합하며,
9종 오류 재현과 복합 문제는 이후 프로젝트 시간에 나누어 반복한다.
상세 범위는 [개선 계획](recovery-upgrade-plan.md), 운영은 [복구 운영안](recovery-instructor-guide.md)을 따른다.
학생용 시작점은 [원리와 복구](../labs/recovery/index.html)다.
현재 개선 브랜치는 결과 검토 단계이며 사용자 승인 없이 main에 병합하지 않는다.

- 정규 수업: 4시간
- 운영 방식: 짧은 설명 → 결과 예측 → 실행 → 관찰 → 실패 → 복구 → 설명
- 이후 반복: Java 수업과 팀 프로젝트에서 같은 작업 흐름을 계속 사용
- 4시간 종료 의미: 프로젝트 시작 가능
- 최종 의미: 안내 없이 팀 Git 흐름 독립 수행

## MUST / SHOULD / COULD

### MUST

- Git과 GitHub의 역할 구분
- Working Tree, Staging Area, Repository
- `status`, `diff`, `add`, `commit`, `log`
- `.gitignore`와 비밀정보 제외
- `switch -c`를 이용한 기능 브랜치 작업
- `fetch`, `pull`, `push`와 로컬·원격 구분
- Pull Request 생성, 리뷰, 수정, 병합
- 충돌 표시 해석과 충돌 해결
- `restore`, `restore --staged`, `revert`
- 위험 명령을 실행하기 전 데이터 손실 범위 확인

### SHOULD

- push 거절 진단과 해결
- 원격 추적 브랜치 이해
- 커밋 그래프 읽기
- 잘못된 브랜치에서 시작한 작업 이동
- PR 설명과 리뷰 품질

### COULD

- detached HEAD와 `reflog`
- stash
- reset 모드 비교
- Fork와 upstream
- branch protection 설정

## 4시간 수업 흐름

| 블록 | 핵심 문제 | 개념·시연 | 학생 실습 | 체크포인트 |
|---|---|---|---|---|
| 1. 상태와 커밋 | 어떤 파일이 다음 커밋에 들어가는가? | 상태, diff, stage, commit, ignore | 파일 3개 중 필요한 변경만 두 번 커밋 | `status`, `diff`, `log`로 상태 설명 |
| 2. 브랜치 | main을 깨뜨리지 않고 기능을 만드는가? | branch, switch, merge | 기능 브랜치 생성·변경·병합 | 작업 위치와 커밋 그래프 설명 |
| 3. 원격과 PR | 내 작업을 팀에 안전하게 전달하는가? | origin, fetch, pull, push, PR | 기능 브랜치 push·PR·리뷰 반영 | PR과 리뷰 반영 상태 확인 |
| 4. 충돌과 복구 | 동시 수정과 실수를 어떻게 복구하는가? | conflict, restore, revert, 위험 명령 | 2인 충돌·합의·해결·검증 | 해결 커밋과 선택 근거 설명 |

총 240분: 준비·접속 점검 15분 + 상태 45분 + 브랜치 40분 + 휴식 10분 + 원격·PR 55분 + 휴식 10분 + 충돌·기초 복구 45분 + 확인·지연 대응 20분.
각 개념 블록은 설명·시연보다 학생 실행에 충분한 시간을 배정한다. 시간은 운영 초안이며 실제 학생 소요시간으로 재검증한다.
지연 시 심화 생성·반복 협업·stash/reflog·복합 진단은 다음 시간으로 넘긴다. 기본 commit·branch·PR·충돌 확인을 건너뛰고 PASS로 처리하지 않는다.
인증이 해결되지 않은 학생은 로컬 원격으로 기술 흐름을 이어가되 GitHub PR 항목은 미완료로 남긴다.

## 성장형 실습 저장소

```text
team-profile/
├─ README.md
├─ members/
│  ├─ student-a.md
│  └─ student-b.md
├─ team.md
└─ .gitignore
```

저장소 생성부터 PR 병합까지 하나의 이력을 계속 발전시킨다. 단절된 명령어 문제로 바꾸지 않는다.

## 강사 체크포인트

1. 명령 전: 학생이 예상 결과를 말한다.
2. 명령 후: `status`, `diff`, `log` 중 적합한 근거를 보여준다.
3. 실패 후: 오류 메시지를 지우거나 숨기지 않고 원인을 설명한다.
4. 복구 전: 사라질 수 있는 데이터를 말한다.
5. 완료 후: 커밋, 브랜치, PR, 리뷰 상태를 화면에서 확인하고 학생이 설명한다.

## 단계별 완료 기준

### 4시간 직후 — 기초 PASS

- 기능 브랜치에서 의미 있는 커밋 2개 이상
- `.gitignore` 적용
- push와 PR 생성
- 동료 리뷰 1개 작성
- 간단한 충돌 해결
- 잘못 stage한 파일 복구
- 현재 상태를 자기 말로 설명

### 반복 실습 3회 후 — 적용 PASS

- 안내서 없이 `main 최신화 → 기능 브랜치 → commit → push → PR` 수행
- push 거절 또는 충돌을 상태 확인 후 해결
- 리뷰 의견을 새 커밋으로 반영
- 질문할 때 브랜치, `status`, 오류 메시지, 시도한 방법 제공

### 팀 프로젝트 진입 전 — 독립 수행 PASS

- Issue부터 PR 병합까지 전체 흐름 독립 수행
- 다른 사람의 작업을 덮어쓰지 않고 원격 변경 반영
- 비밀정보와 생성 파일 제외
- 현재 수업: Markdown 내용·누락·충돌 표시 검증. 이후 코드 프로젝트: 해당 기능 실행·테스트 검증
- 위험 명령 없이 상황에 맞는 복구 선택
- Git 이력으로 자신의 작업 과정을 설명
