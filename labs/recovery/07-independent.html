조건이 달라도 혼자 해결할 수 있을까?

정답 순서를 기억했는지가 아니라, 처음 보는 상태에서 보존·선택·검증을 수행하는지 확인합니다. 제출 입력란이나 별도 제출물은 없습니다.

첫 단계: 안내를 줄이기

  1. 첫 연습은 원리와 그림을 읽고 복구 절차를 펼쳐 수행합니다.
  2. 다음 연습은 절차를 닫고 상태 확인 명령만 참고합니다.
  3. 마지막 연습은 아래 요구사항만 읽고 진단부터 스스로 수행합니다.

새 독립 진단: 원인을 먼저 알려주지 않습니다

D2/D3는 진행자가 보낸 중립적 이름의 연습 ZIP과 아래 카드만 받습니다. 본인 프로젝트 ZIP은 사용하지 않습니다. 안내된 SHA256을 확인하고 Windows 탐색기로 새 폴더에 압축을 풉니다. .git 폴더가 포함되었는지 확인한 뒤 그 폴더에서 git status를 실행합니다. 원격 경로가 필요한 D1은 오류 카드 진단과 안내형 실행을 구분합니다. 문제를 직접 준비했다면 원인을 이미 아는 안내형 연습입니다. 독립 진단으로 판정하지 않습니다. 혼자라면 기존 실습으로 복구를 연습하고, 이후 진행자와 조건을 바꾸어 확인하세요.

순서: 증상 확인 → 가설 2개 → 구분할 근거 → 보존 → 선택 → 검증. 첫 오류를 지우지 말고 현재 폴더와 상태부터 읽습니다. 제출물이나 입력란은 없습니다.

D1 · 내 변경이 올라가지 않는다

증상: push가 실패했습니다. 원인은 공개하지 않습니다. 목표는 올바른 대상에 필요한 커밋을 전달하거나, 본인 권한 밖이면 안전하게 도움을 요청하는 것입니다. 기존 문서·새 메모·동료 커밋을 잃으면 안 됩니다.

먼저 질문하세요: 전송할 원격과 브랜치가 맞는가? 로컬·원격 이력 차이가 있는가? 이 계정이 쓰기 권한을 갖는가? 확인되지 않은 가설로 명령을 실행하지 않습니다.

힌트 1 · 무엇을 확인할까?

오류 원문, 현재 폴더, status, branch -vv, remote -v를 비교합니다. 원격 주소에 토큰이 있다면 화면 공유 전에 가립니다. 이력 비교는 fetch 성공 후에만 신뢰합니다.

힌트 2 · 증상 구분
오류 단서다음 확인피할 행동
no upstream branch / no refspecs specified올바른 원격·브랜치 연결 및 push.default 설정불필요한 reset
non-fast-forward / fetch firstfetch 후 양쪽 전용 커밋동료 변경을 덮는 force push
permission denied / 403주소·사용 계정·접근권한인증서 검사 해제·토큰 공유

권한 오류는 이력 병합으로 해결되지 않습니다. 403만으로 원인을 하나로 단정하지 않습니다.

통과: 선택 이유, 보존한 작업, 원격 반영 증거를 설명합니다. 권한 문제가 확인된 경우 필요한 정보만 담아 담당자에게 요청하고 작업을 보존한 것도 올바른 종료입니다.

D2 · 보관한 작업을 되살렸는데 충돌했다

현재 README에는 충돌 표시가 있습니다. 목표는 최신 안내와 미완성 아이디어를 합의된 문장으로 함께 반영하고 새 메모를 남기는 것입니다. 보관 항목은 내용 검증 전 삭제하지 않습니다.

힌트 1 · 작업 종류부터 구분

status와 stash 목록을 읽습니다. 충돌 표시가 있다는 이유만으로 진행 중인 merge라고 단정하지 않습니다. 원래 보관 내용과 현재 파일을 비교합니다.

힌트 2 · 복구 경계

stash apply 충돌에는 일반적인 merge --abort 절차를 그대로 적용하지 않습니다. 합의 후 문서를 편집하고 stage·검증합니다. apply를 반복하거나 stash를 먼저 drop하지 않습니다. 추가 편집이 섞여 의도가 불명확하면 현재 파일을 보존하고 도움을 요청합니다.

통과: 합의 문장, 새 메모, stash 항목의 존재와 미해결 index가 없음을 각각 확인합니다. clean만으로 성공을 판정하지 않습니다.

D3 · 잘못된 변경을 취소하다가 멈췄다

팀이 이미 사용한 변경을 취소하는 중입니다. 그런데 그 뒤에 승인된 문장도 있습니다. 뒤의 승인된 내용은 유지해야 합니다. 먼저 계속할지, 취소 작업을 중단하고 팀에 확인할지 선택하세요.

힌트 1 · 시간 순서 읽기

status, log, 취소 대상의 show로 “취소 대상 → 이후 변경 → 현재 상태”를 구분합니다. 같은 줄에 후속 변경이 있었는지 확인합니다.

힌트 2 · 중단과 계속

의도가 불명확하면 진행 중인 revert를 abort하고 확인합니다. 합의했다면 최종 문장으로 편집·add 후 continue합니다. 결과가 이미 HEAD와 같아서 빈 작업 안내가 나올 수 있습니다. 그때는 status를 읽고 skip 여부를 판단합니다. 무조건 새 커밋을 만들려고 문서를 바꾸지 않습니다.

통과: 승인된 문장과 공유 이력이 유지되고, 진행 중인 취소 작업·미해결 충돌이 없습니다. 커밋 수보다 목표 달성을 검증합니다.

반복 협업 · 내 PR을 고치는 동안 main이 바뀐다

2인, 수업용 GitHub 저장소, 25~35분. 기존 4시간 이후 반복 실습입니다. README와 team.md만 사용합니다.

  1. A는 연락 규칙 PR을 열고 B는 모호한 문장을 리뷰합니다.
  2. A가 고치는 동안 B는 회의 규칙 PR을 별도로 만들고 A의 검토 후 main에 반영합니다.
  3. A는 리뷰 수정 커밋을 만든 뒤 최신 main과 자신의 브랜치 차이를 진단하고 통합합니다.
  4. 같은 문장이 충돌하면 합의한 문장으로 해결하고 diff·문서 내용을 재검증한 뒤 push합니다.
  5. B는 갱신된 변경을 다시 리뷰합니다. 승인 후 병합하고 둘 다 main을 최신화합니다.
  6. 역할과 문장을 바꾸어 한 번 더 반복합니다.

완료: 두 학생의 필요한 문장·리뷰 수정이 최종 문서에 남고 불필요한 파일이 PR에 없습니다. 각자 로컬 main과 원격의 관계를 설명합니다. 혼자 로컬 원격으로 연습하면 실제 리뷰·승인을 완료한 것으로 세지 않습니다.

독립 수행 판정: 성공과 도움의 양을 구분

단계제공하는 안내확인
안내형준비·원리·명령 전체실행 후 상태를 설명
제한 힌트형증상·목표·힌트 1구분 근거로 방법 선택
독립형비공개 준비 저장소·증상·보존 조건힌트 없이 다른 조건 3회 + 실제 팀 작업 1회

힌트를 봐도 연습은 성공할 수 있습니다. 다만 독립 수행으로 판정하지 않고 조건을 바꿔 다시 시도합니다. 질문과 안전한 중단은 실패가 아닙니다.

복합 문제 A · 다른 PC에서 이어서 작업

실습 MD에서 remote 상황을 준비합니다. 내 커밋도 있고 동료의 커밋도 있으며 notes에는 미완성 작업이 있습니다. 목표는 양쪽 커밋을 통합해 원격에 반영하되 미완성 notes는 원격에 올리지 않고 현재 PC에 남기는 것입니다.

  • origin/main의 정보가 최신인지 어떻게 확인할까요?
  • 미완성 notes와 내 커밋은 같은 방법으로 보존해야 할까요?
  • 완료 후 clean이어야 할까요, 변경이 남아야 할까요?

복합 문제 B · 잘못된 브랜치와 긴급 전환

실습 MD에서 branch 상황을 준비합니다. feature에 미완성 README 변경이 있고 main으로 전환하면 거절됩니다. main에서 기준 내용을 확인한 뒤 돌아와 작업을 그대로 이어가세요. 별도 파일을 잃거나 미완성을 main에 커밋하면 안 됩니다.

변형: 새 미추적 메모가 추가되어 있다면 보관 방법과 검증 항목이 어떻게 달라지나요?

복합 문제 C · 충돌을 취소할까, 해결할까?

실습 MD에서 delete-conflict 상황을 준비합니다. A는 문서를 수정했고 B는 제거했습니다. 첫 시도에서는 요구사항이 확정되지 않았으므로 병합을 안전하게 중단하세요. 다시 병합한 뒤 “문서는 유지하되 최신 안내를 반영한다”라는 합의에 따라 해결하세요.

파일 내용, 미해결 index 항목, commit 부모와 status를 각각 확인합니다. 다른 사람이 변경한 의도를 확인하지 않고 한쪽을 버리면 통과할 수 없습니다.

공통 통과 기준

확인관찰 가능한 결과
진단현재 branch, staged/unstaged, 공유 여부를 근거로 설명
보존보존 대상 파일과 커밋을 먼저 식별

검증파일 내용과 이력, 실제 코드인 경우 실행 결과 확인

오류가 없어졌다는 말만으로는 통과하지 않습니다. 상태가 다른 세 문제에서 연속으로 독립 수행한 뒤 실제 프로젝트 첫 작업에서도 같은 기준을 확인합니다. 힌트가 필요하면 재실습하며 질문 자체를 실패로 취급하지 않습니다.

원격수업 운영

학생은 화면 공유로 현재 상태와 판단 이유를 1~2분 설명합니다. 강사는 대신 명령을 입력하지 않고 “무엇이 사라지면 안 되나?”, “어떤 출력이 성공을 증명하나?”를 질문합니다. 짝이 없으면 local remote 실습으로 기술 흐름을 연습하고, 실제 PR 리뷰는 강사와 교대로 진행합니다.

4시간 본 수업에서는 상태·브랜치·동기화·충돌의 대표 사례를 다룹니다. 이후 수업 시작마다 10~15분 복구 문제를 반복합니다. 어려운 복합 문제는 20~30분을 확보하며, 이 시간은 기존 4시간에 숨겨 넣지 않습니다.
