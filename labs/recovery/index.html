Git과 Markdown만으로 시작하기

학생 준비물은 Git과 기본 텍스트 편집기입니다. 별도 언어 런타임·실습 생성기를 설치하지 않습니다. Windows 기본 PowerShell에서 페이지에 있는 명령을 한 줄씩 실행하거나 편집기로 같은 내용을 작성합니다.

직접 실습 Markdown 다운로드

각 상세 페이지는 새 연습 폴더 생성 → 기본 문서 커밋 → 문제 상황 만들기 → 예상 상태 확인 순서로 시작합니다. git --version이 버전을 출력하는지 확인하세요. GitHub 협업에만 계정과 네트워크가 필요하며, 로컬 원격 실습은 같은 PC에서 가능합니다.

Set-Content는 파일을 덮어쓰므로 반드시 페이지에서 만든 새 연습 폴더에서 실행합니다. 주석의 예상 오류 외에는 실행을 멈추고 위치와 오류를 확인합니다.

1. 오류가 나면 먼저 현재 상태 읽기

Get-Location
git rev-parse --show-toplevel
git branch --show-current
git status
git diff
git diff --staged
git log --oneline --graph --decorate -8

첫 두 줄은 다른 저장소에서 명령을 실행하는 실수를 막습니다. branch 출력이 비면 detached HEAD일 수 있으므로 status를 읽습니다. status는 진행 중인 병합과 충돌도 알려줍니다. diff는 작업 트리와 index, staged diff는 index와 HEAD를 비교합니다. 두 출력이 다른 것은 오류가 아니라 서로 다른 상태를 비교하기 때문입니다.

관찰해석과 다음 판단
MM README.mdstage한 뒤 다시 편집했습니다. 첫 M은 index, 두 번째 M은 작업 트리의 차이입니다.
?? draft.md아직 추적되지 않은 파일입니다. 일반 diff나 기존 커밋만으로 보존 여부를 증명할 수 없습니다.
UU README.md양쪽 수정 충돌이 미해결입니다. 파일을 합의해 편집한 뒤 stage해야 합니다.
not a git repository위치를 먼저 확인합니다. 해결하려고 아무 폴더에 git init을 반복하지 않습니다.

원격이 있는 저장소에서만 git remote -v로 대상 확인 후 git fetch origin을 실행합니다. 이후 git log --oneline --left-right HEAD...origin/main에서 <는 현재 브랜치에만, >는 origin/main에만 있는 커밋입니다. origin/main은 서버 자체가 아니라 마지막 fetch로 갱신한 로컬 참조입니다. 브랜치명이 다르면 실제 이름으로 비교합니다.

2. 보존할 것을 구분하고 방법 선택하기

커밋을 가리키는 구조 이름을 하나 더 만드는 것은 커밋 보존에 도움이 되지만, 편집 중인 파일이나 새 파일까지 저장하지는 않습니다. 반대로 stash는 로컬 임시 보관이며 다른 PC로 자동 전송되지 않습니다. 비밀정보는 커밋이나 공유용 백업에 넣지 않습니다.

현재 상태와 목적선택멈춰야 할 조건
잘못 stage, 파일 편집은 유지restore --staged 대상파일파일까지 되돌리는 restore와 혼동하면 중단
편집을 잠시 보관하고 이동stash push, 새 파일도 필요하면 -u충돌 진행 중이거나 ignored 파일도 보존해야 하면 먼저 별도 보존 계획
이미 공유한 잘못된 일반 커밋 취소revert로 취소 커밋 추가merge 커밋 취소 또는 팀 의도가 불명확하면 협의
아직 공유하지 않은 이력 정리보존 참조 확보 후 reset 영향 검토다른 사람이 사용 중이거나 공유 여부를 모르면 실행하지 않음
커밋이 안 보임reflog와 show로 확인 후 구조 브랜치 생성reflog는 미커밋 파일 백업이 아니며 영구 보관도 아님

stash -u는 untracked도 포함하지만 ignored 파일은 포함하지 않습니다. apply는 저장 항목을 남기므로 내용을 확인한 뒤 drop 여부를 결정합니다. 단계별 명령은 보존·복구 실습을 따릅니다. Git 공식 stash 설명 · reset의 변경 범위

3. 복구하다 다시 실패했을 때

명령을 반복하지 말고 status부터 다시 읽습니다. merge 충돌이면 합의해 해결할지, 진행 중인 merge를 중단할지 선택합니다. merge --abort도 병합 전 미커밋 변경을 항상 복원한다는 보장은 없으므로 시작 전에 보존합니다.

stash apply 충돌은 merge --abort로 되돌리는 일반 병합과 다릅니다. stash 항목을 삭제하지 말고, 현재 파일과 원래 stash 내용을 비교해 해결합니다. 적용 후 다른 편집까지 했다면 덮어쓰지 말고 도움을 요청합니다. 잘못된 브랜치에서 시작했다면 현재 브랜치와 미커밋 변경을 확인하기 전 강제 전환하지 않습니다.

권한 오류·비밀정보 노출·공유 이력 재작성·팀원의 변경 의도가 불분명한 충돌은 혼자 강행하지 않습니다. 도움 요청에는 작업 목표, 브랜치, status, 오류 원문, 직전 명령, 보존할 작업을 전달하세요. 토큰·비밀번호·개인 경로는 가리고 화면 공유합니다.

4. 복구 성공은 오류가 없다는 뜻보다 넓습니다

  1. 파일: 본인·동료의 필요한 내용이 남았나요? 새 파일도 확인했나요?
  2. 내용: README와 team.md의 목표·소개 문장이 의도와 같고 누락은 없나요?
  3. 상태: 미해결 충돌이 없고 staged 범위가 맞나요?
  4. 이력: log와 show로 취소·병합·보존 커밋을 설명할 수 있나요?
  5. 원격: 실제 공유가 목표였다면 fetch 후 해당 원격 브랜치와 비교했나요?

미완성 작업을 되살린 실습은 변경이 남아야 성공입니다. 무조건 clean으로 만들려고 파일을 삭제하지 않습니다. 반대로 다음 모듈이 clean을 요구한다면 필요한 변경을 검토·커밋한 뒤 이동합니다.

수업을 놓쳤거나 다시 연습할 때

Get-Location과 git status로 위치를 확인하고 기존 폴더를 남겨둡니다. 같은 페이지의 시작 상태 만들기를 다시 실행하면 새 고유 폴더가 만들어집니다. 실제 프로젝트에서는 init·reset·clean으로 수업 위치를 맞추지 않습니다.

기본 4시간은 상태 → 브랜치 → 원격 → PR → 충돌, 심화 복구는 이후 반복 실습입니다. 명령을 따라 한 뒤에는 안내를 접고 현재 상태·선택 이유·보존 결과를 설명하세요.

읽기와 실습을 함께 진행하세요

  1. 내부 원리를 그림으로 읽습니다.
  2. 문제가 들어 있는 새 연습 저장소를 만듭니다.
  3. 해결 절차를 펼치기 전에 진단과 선택 이유를 말합니다.
  4. 명령 결과뿐 아니라 파일 내용과 이력도 검증합니다.
  5. 변형 문제에서는 명령 안내 없이 다시 수행합니다.
이 과정은 4시간 수업 전체에 추가로 몰아넣는 내용이 아닙니다. 기본 개념은 기존 시간에 통합하고, 복구 연습은 이후 프로젝트 시간에 나누어 반복합니다.

직접 만드는 9가지 상황

실습 MD에는 staged·branch·committed·remote·conflict·delete-conflict·stash·lost·shared의 준비 명령과 예상 결과가 있습니다. 상태·브랜치·동기화·충돌·복구 페이지에서 상세 원리와 해결 절차를 이어 읽습니다.

remote는 같은 PC의 두 폴더와 bare 저장소로 동기화를 재현합니다. 실제 GitHub PR·권한·리뷰 검증을 대신하지 않습니다.
