MODULE 05

Pull Request로
설명하고 리뷰하기

기능 브랜치를 PR로 전달하고 구체적인 동료 리뷰를 새 커밋으로 반영한 뒤 병합합니다.

2인 필수Pull Request리뷰 반영

문제 상황

PR은 “merge 해주세요” 버튼이 아닙니다. 작성자는 변경 목적과 검증을 설명하고, 리뷰어는 구체적인 근거로 변경을 확인합니다.

PR용 기능 준비

  1. Issue에 작업 목적과 완료조건을 적습니다.
  2. 최신 main에서 기능 브랜치를 만듭니다.
  3. members/이름.md와 Java 중 하나를 변경합니다.
  4. 실행 또는 파일 검증 후 push합니다.
git switch main
git pull --no-rebase origin main
git switch -c feature/이슈번호-profile
# 작업
git status
git diff
# 실행 검증
git add 필요한-파일
git commit -m "feat: 작업 목적"
git push -u origin feature/이슈번호-profile

PR 작성

제목

구현한 기능을 동사와 대상으로 표현합니다. “수정”, “완료”처럼 범위를 알 수 없는 제목은 피합니다.

## 목적
어떤 문제 또는 요구사항을 해결했는가?

## 변경
어떤 파일과 동작이 바뀌었는가?

## 검증
어떤 명령을 실행했고 결과는 무엇인가?

## 확인 요청
리뷰어가 특히 확인할 부분은 무엇인가?

리뷰어 미션

  1. Files changed에서 변경 범위가 Issue와 일치하는지 봅니다.
  2. 관계없는 파일, 비밀정보, 생성 파일이 없는지 봅니다.
  3. 구체적인 한 줄에 질문 또는 수정 요청을 남깁니다.
  4. 검증 결과가 재현 가능한지 확인합니다.

통과하지 않는 리뷰

“좋습니다”, “확인”, “LGTM”만 작성

통과하는 리뷰

파일과 줄, 이유, 기대 결과가 포함된 질문 또는 제안

작성자 미션 — 리뷰 반영

기존 커밋을 지우거나 force push하지 않고 새 커밋을 추가합니다.

git switch feature/이슈번호-profile
# 리뷰 내용 수정
git diff
# 실행 검증
git add 필요한-파일
git commit -m "fix: address profile review"
git push

병합과 로컬 정리

리뷰 승인과 검증 완료 후 GitHub에서 병합합니다. 이후 로컬 main을 최신화하고 병합된 기능 브랜치와 차이가 없는지 확인합니다.

git switch main
git pull --no-rebase origin main
git log --oneline --graph --decorate -8
git branch -d feature/이슈번호-profile
git status

브랜치 삭제 전

PR이 실제로 병합됐고 main에 커밋이 들어왔는지 확인합니다. 삭제는 정리 단계이며 학습 완료 증거를 대신하지 않습니다.

말로 설명

  • commit과 PR은 각각 어떤 단위인가?
  • 리뷰 반영을 새 커밋으로 남기면 무엇이 좋은가?
  • Request changes가 실제 병합을 막으려면 저장소에 무엇이 필요한가?
