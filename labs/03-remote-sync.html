MODULE 03

원격 저장소와
push 거절 해결

origin과 원격 추적 브랜치를 구분하고, 원격 커밋 때문에 push가 거절되는 상황을 안전하게 해결합니다.

개인 + 2인originpush rejected

문제 상황

내 로컬에는 없지만 원격에는 있는 커밋 때문에 push가 거절될 수 있습니다. force push로 덮지 않고 원격 상태를 읽어 안전하게 합칩니다.

실습 전 확인

GitHub 저장소 URL에 개인 토큰이나 비밀번호를 넣지 않습니다. HTTPS 인증은 Git Credential Manager 브라우저 로그인을 사용합니다.

원격 연결과 추적 관계

git remote add origin 저장소-URL
git remote -v
git push -u origin main
git branch -vv

예측

-u 이후 단순 git push가 가능한 이유를 예상합니다.

관찰

branch -vv에서 로컬 main이 어떤 원격 브랜치를 추적하는지 확인하고 말합니다.

미션 — 기능 브랜치 push

  1. 새 기능 브랜치를 만들고 README에 한 줄을 추가합니다.
  2. 커밋 후 원격 기능 브랜치로 push합니다.
  3. GitHub에서 브랜치가 보이는지 확인합니다.
git switch -c feature/remote-practice
# README 수정
git add README.md
git commit -m "docs: add remote practice note"
git push -u origin feature/remote-practice
git branch -vv

실패 재현 — push rejected

A와 B가 같은 원격 main을 사용합니다. A가 먼저 커밋을 push한 뒤, B는 이전 main에서 다른 커밋을 만들고 push합니다.

A 학생B 학생
main 최신화 → README 수정 → commit → pushA의 push 전에 받은 main에서 README 다른 부분 수정 → commit
push 완료 실행 확인pull 없이 push하여 rejected 오류 보존

오류 원문

진단하고 해결

git status
git branch --show-current
git fetch origin
git log --oneline --graph --decorate --all -10
git diff main..origin/main

그래프를 본 뒤 팀 규칙에 맞게 원격 변경을 반영합니다. 이 과정에서는 merge 기반 pull을 사용합니다.

git pull --no-rebase origin main
# 충돌이 있으면 MODULE 04 절차로 해결
git status
# Java 또는 파일 결과 검증
git push origin main

금지

rejected는 “강제로 밀어도 된다”는 뜻이 아닙니다. push --force는 원격 커밋을 잃게 할 수 있습니다.

말로 설명

  • fetch는 작업 파일을 바로 바꾸는가?
  • origin/main은 GitHub 자체인가, 로컬의 원격 추적 포인터인가?
  • push 거절 때 force가 위험한 이유는?
